# LSP-client architecture for the Teal IntelliJ plugin

Status: accepted

The original ask that started this project was an 8-step plan for a full custom IntelliJ plugin — its own JFlex lexer, Grammar-Kit PSI/parser, and annotator — with that plan itself noting it was "only worth it if the LSP4IJ route is too limited." We decided that trade-off first: [Prototype the LSP-client route](../../.scratch/teal-plugin/issues/01-prototype-lsp-client-route.md) validated LSP4IJ wiring `teal-language-server` (an existing, actively-maintained Teal LSP implementation) against a real project, with diagnostics, hover, and go-to-definition all working via configuration alone — no fork or patch to `teal-language-server` needed. [Lock the architecture decision](../../.scratch/teal-plugin/issues/02-lock-architecture-decision.md) applied the rule set in advance ("a genuine failure — a fork/rewrite of `teal-language-server`, or LSP4IJ unable to deliver `.tl` support at all — would mean native-PSI instead") and locked **LSP-client**: the companion plugin's own code is limited to `.tl` file-type registration and bundling a syntax-highlighting grammar, with all language intelligence delegated to LSP4IJ + `teal-language-server`.

**Considered and rejected**: native-PSI (full custom lexer/PSI/parser/annotator, independent of any LSP server) — the plan's default-sounding option, and the more IntelliJ-native one, but far more code to build and maintain for no validated benefit once the LSP-client route proved to work cleanly.

**Consequences**: go-to-definition, hover, and completion are IntelliJ IDEA's stock LSP4IJ UX (not custom IntelliJ-native UX like structure view or refactoring) — accepted, since the destination was daily-use value, not IDE-native polish. Highlighting still needs its own answer since `teal-language-server` has no `semanticTokensProvider`; see the MVP spec ([.scratch/teal-plugin/issues/03-write-mvp-spec.md](../../.scratch/teal-plugin/issues/03-write-mvp-spec.md)) for the TextMate-based approach chosen for that gap.

**Amendment — Find Usages breaks the "zero language-intelligence code" bet.** `teal-language-server` doesn't implement `textDocument/references` at all, so LSP4IJ has nothing to delegate to for Find Usages — unlike highlighting, there's no config-only or LSP4IJ-feature-level answer. Two ways to close that gap were considered: patch `textDocument/references` into `teal-language-server` upstream (a real, scoped, testable patch — prototyped and validated against a local build), or implement it inside this plugin. The plugin-side route was chosen instead, to avoid depending on an upstream merge and on every user running a patched server. It's implemented as a JSON-RPC proxy (`TealReferencesProxyConnectionProvider` / `TealReferencesProxyCore`, see [spec.md](../../.scratch/teal-plugin/spec.md)'s Feature 3) sitting between LSP4IJ and the real process: it fakes the `referencesProvider` capability and answers references requests itself by reusing the real server's own `textDocument/definition` as a black-box oracle, rather than reimplementing Teal's scope/type resolution. This is real, maintained plugin-side logic — the one deliberate exception to this ADR's "all language intelligence delegated to LSP4IJ + `teal-language-server`" — accepted because the alternative (an upstream patch) trades a small, contained amount of in-repo complexity for a dependency this project doesn't control the timeline of.

**Second amendment — the proxy becomes the general gap-filler (missing-require quick fix).** `teal-language-server` doesn't advertise `codeActionProvider` either, so an `unknown type X` diagnostic has no quick fix. Three routes were weighed:
- an IntelliJ-native quick fix attached to LSP4IJ's diagnostics, rejected because LSP4IJ has no clean extension point for adding fixes to its own diagnostics;
- an upstream patch, rejected for the same timeline-dependency reason as Find Usages;
- answering `textDocument/codeAction` in the existing JSON-RPC proxy, which LSP4IJ then shows as a stock Alt+Enter fix.

The proxy route was chosen. The proxy is renamed from `TealReferencesProxy*` to `TealLspProxy*` to reflect its broader job. It is now the single sanctioned home for plugin-side language intelligence: any future server gap is filled there, as an LSP answer, rather than as IntelliJ-native UI code. Unlike Find Usages, this fix can't use the server as an oracle for where a type is declared (there is no `workspace/symbol`), so it does its own lightweight workspace scan for `global` declarations. That is a deliberate step further from "delegate everything", accepted because it stays text-level and small. See [spec.md](../../.scratch/teal-plugin/spec.md)'s Feature 4.

**Third amendment: replace teal-language-server with our own Lua server built on `tl`.** The proxy's features are drifting toward text-level guesswork. Find Usages scans identifiers and probes `textDocument/definition` once per candidate. The missing-require quick fix and require navigation don't use the server at all. The server has the scope and type data these features need, but exposes none of it over LSP. That data comes from `tl` anyway. `teal-language-server` is about 3.9k lines of Lua, mostly LSP plumbing (framing, document sync, logging, URI helpers). Every language answer it gives comes from `tl`'s library API: `tl.check`, the type report, and `tl.symbols_in_scope`. The proposal is to swap that wrapper for a small Lua LSP server of our own, bundled in the plugin and loading `tl` as a library.

What changes and what doesn't:
- **The LSP-client architecture stays.** LSP4IJ is still the client, all UX is still stock LSP4IJ UX, and the TextMate route still does highlighting. Only the process on the other end of the stream changes.
- **The proxy is retired.** References, code actions and require navigation move into the server as ordinary LSP handlers backed by the type report. The server becomes the single home for plugin-side language intelligence, replacing the role the second amendment gave the proxy.
- **This deliberately reverses the original rule set.** That rule set treated "a fork/rewrite of `teal-language-server`" as a failure that would push us to native-PSI. That rule was about avoiding reimplementing Teal's typechecker. This proposal doesn't do that. It rewrites only the LSP glue and keeps `tl` as the sole source of truth for types and scopes. Native-PSI remains rejected.

**Considered options**:
- **Status quo (`teal-language-server` plus the proxy).** Zero migration cost. Every new feature has to be reconstructed from definition probes or text scans, and the proxy's per-token probing gets slower as files grow.
- **Upstream patches to `teal-language-server`.** Rejected, as in the first two amendments: we don't control the merge or release timeline, and users would need a patched server.
- **Fork `teal-language-server` (MIT) into the repo.** This is the fastest start, since all its features work on day one. We would also inherit its native `luv` dependency and its `lusc` async runtime. Worth considering as a starting point to strip down rather than as the end state.
- **A non-LSP helper script (Kotlin sends JSON requests to a Lua script that calls `tl`).** Rejected: we would have to rebuild in IntelliJ-native code the diagnostics, hover and completion UX that LSP4IJ already provides.

**Consequences**:
- **Install story.** Users still need a Lua interpreter and the `tl` rock (`luarocks install tl`). They no longer need `teal-language-server` or its native dependencies: `luv`, which needs cmake to build, and `ltreesitter`, which the server uses to find the node under the cursor. `tl`'s own tokens (`tl.lex`, `tl.get_token_at`) look like enough to replace tree-sitter. A plain blocking stdio loop in pure Lua avoids `luv` entirely. That loop can't debounce `didChange`, and the [minimal-server prototype](../../.scratch/teal-plugin/prototypes/minimal-server/README.md) shows it doesn't need to. On a reused env, re-checks take about 2–17 ms for picolo-rpg's files (up to 924 lines). Only a 15k-line file (`tl.tl`) is slow, at about 350 ms.
- **References become cheap and exact.** The type report's `symbols_by_file` resolves every identifier in picolo-rpg's `main.tl` (2.2k tokens) to its declaration in 6.6 ms in-process. The proxy needs one definition request per token for the same job. The lookup borrowed from teal-language-server is a linear scan and needs a binary search to stay fast on large files.
- **The env lifecycle is ours to design.** A `tl` env holds the bootstrapped globals (such as `love`) and also caches every required module. Reusing one env across edits is fast, but its type table keeps growing: 4.8k → 22.5k entries after 50 edits of `main.tl`. teal-language-server reuses one env for the whole session, so it probably has the same growth. A fresh env per edit has no growth but costs about 88 ms per edit, and it is the only way to pick up changes to a required module. **Policy: reuse one env, and rebuild it after N edits or on save.** A save of any `.tl` document triggers a rebuild, because a saved file may be a module another file requires. The edit count is the backstop for long unsaved sessions. N defaults to 100. On `main.tl`, the live heap grows about 180 KB per edit (+13 MB → +31 MB by edit 100, +84 MB by edit 400). Per-edit check time stays flat at about 17–20 ms, so N only bounds memory. A rebuild costs about 60 ms once, which adds under 1 ms per edit spread over 100 edits. Files changed outside the editor (`git checkout`, codegen) aren't covered until the next save or the N-th edit; handling those means watching files through `workspace/didChangeWatchedFiles`, which is out of scope for now.
- **API dependency.** We now depend directly on `tl`'s library API, not just its behaviour through someone else's server. The type-report shape and `symbols_in_scope` are not documented as stable. We need tests that run against the `tl` versions we claim to support, and a clear error when an unsupported version is found.
- **Lua version compatibility.** The Lua runtime becomes our problem. For example, the `tl` CLI installed under Homebrew's Lua 5.5 fails at startup with `attempt to assign to const variable 'entry'`. The bug is in the CLI script, which assigns to a `for` loop variable (read-only in 5.5). The prototype confirmed that `tl` 0.24.8 loads and checks fine as a library on Lua 5.5.1. Support for Lua 5.1 through 5.5 and LuaJIT needs an explicit decision.
- **Ownership.** The repo gains a second language (Lua or Teal) with its own tests. The existing proxy JUnit tests, which already drive a real server over raw stdio, can be pointed at the new server to catch regressions during migration.
- **Migration order.** The proxy keeps working throughout. Move diagnostics, hover, definition and completion first to reach parity, then move each proxy feature onto type-report data. Delete the proxy when nothing passes through it.
